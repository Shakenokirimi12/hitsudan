# 筆談ボード (Hitsudan)

ペンタブに手書きした内容を Claude に読ませ、視覚的に指示を出すための macOS ネイティブアプリ。

- Swift + AppKit のみ。外部依存ゼロ、単一バイナリ
- **HUION Kamvas 13 Gen3 (GS1333) を IOHIDManager で直接読む** — ベンダードライバなしでも筆圧・傾き・ボタンが取れる
- アプリ自身は AI を呼ばない。動いている Claude Code セッションが MCP サーバ経由でボードを読み書きする（**APIキー不要**）
- **Kamvas はボード専用のディスプレイになる** — ペンはボードにだけ効き、マウスは Kamvas に入れない

## ビルドと起動

```sh
./build.sh
open Hitsudan.app
```

Xcode 本体は不要（Command Line Tools のみで通る）。

初回は **システム設定 → プライバシーとセキュリティ** で `筆談ボード` に2つの許可を与える。

- **入力監視**
    - 生 HID を読むのに要る。
    - 無いと筆圧が取れず、線幅が一定になる（描画自体は動く）。
- **アクセシビリティ**
    - マウスを Kamvas に入れない制限（イベントタップ）と、express key の再送に要る。
    - 未許可の間はボードの状態行とメニューバーにその旨が出る。許可すると数秒で有効になる。

## 常駐と起動

メニューバー常駐（`LSUIElement`）。普段は Dock にもアプリスイッチャにも出ない。

- **タブレット接続 かつ HID がオープンできている**間だけ、ウィンドウを Kamvas の
  ディスプレイいっぱいに開き、`.regular` に昇格してメニューとショートカットを有効化する
- 抜くと自動でウィンドウを閉じ、デバイスの排他確保を解放して常駐に戻る
- メニューバーから「ログイン時に起動」（`SMAppService`）を切り替えられる。
  システム設定での承認待ちのときは「（承認待ち）」と出し、押すとログイン項目の設定を開く
- 設定（筆圧カーブ・太さ・ペンの割当先・操作パネルの表示）は `UserDefaults` に保存し、
  前面化のたびに復元する
- 設定ウィンドウは右パネルの「設定」か、アプリメニューの「設定…」（⌘,）で開く。
  操作パネルを隠しているときも ⌘, で開ける
- 操作パネルを隠していても、セッションからの依頼や提案が出ている間はパネルを出す
  （「送る」「適用」「破棄」をペンで押せるようにするため）

アイコンは `Resources/icon.svg` が正本。`NSImage` が SVG をネイティブに解釈できるので、
`Tools/makeicon.swift` でラスタライズして `iconutil` に渡している。

## 使い方

| 操作 | |
|---|---|
| ペンで書く | 位置は自前マッピング、筆圧/傾きは生 HID |
| ⌘V / ドラッグ&ドロップ | スクリーンショット等を下敷きにして上から赤で指示を描く |
| ⌘Return | 待っているセッションへ「送る」（指示はキャンバスに手書きする。入力欄は無い） |
| ⌘Z / ⇧⌘Z / ⇧⌘K | 元に戻す / やり直す / すべて消去（消去も ⌘Z で戻せる） |
| ⌘O / ⌘S | 画像読み込み / PNG 書き出し |
| ⌘N / ⌘[ / ⌘] | 新しいページ / 前のページ / 次のページ |
| ⇧⌘P | 操作パネルの表示を切替 |
| Esc / ⌘W | パネルを隠していれば戻す、それ以外はボードを閉じる / ボードを閉じる |
| ⌘, | 設定 |

設定ウィンドウの「ペンの生データ」に生 HID の値（モード・筆圧・傾き・生座標・ボタン）が出る。
ドライバを外したときの動作確認はここを見る。

貼った画像はシートの解像度（3200×2000）に収まるよう縮小してから下敷きにする。

## MCP — セッションとの双方向

主役はこちら。アプリ内で Claude を呼ぶ機能は無い（読むのはセッションの仕事）。

`hitsudan-mcp` は Swift 製・依存なしの stdio MCP サーバ。登録済み:

```sh
claude mcp add --scope user hitsudan -- ~/Development/hitsudan/hitsudan-mcp
```

| ツール | 用途 |
|---|---|
| `read_board` | 「今」の手書き内容を画像で取得。アプリに最新化させてから読むので、ユーザーが「送る」を押していなくても見える。未回収の返信は上書きしない |
| `wait_for_board` | ボードを前面に出し、依頼文を表示して、ユーザーが手書きして「送る」を押すまでブロックして待つ |
| `request_board` | 依頼文を出すだけで待たない。別の作業を進め、送られたら `collect_board` で回収する |
| `collect_board` | `request_board` への返信を回収する |
| `show_on_board` | **AI が生成したものをボードへ**。`svg` / `image_path` / `text`。SVG は macOS がそのまま描画するので図やレイアウト案を渡せる |
| `clear_board` | 消去を提案する |
| `board_status` | 接続・ストローク数・下敷き・未処理の提案・seq |

### ボードから Claude を起こす

MCP では起こせない（下記）が、**ハーネスのフックからなら起こせる**。
コマンドフックの `asyncRewake` は、バックグラウンドで走って**終了コード 2 でモデルを起こす**。

`Tools/board-wake.sh` を `Stop` フックに仕掛けてある。セッションが応答を終えたあとも
バックグラウンドでそのセッション宛ての返信（`replies/<key>.json` の `seq`）を監視し、
ユーザーが「送る」を押した瞬間に exit 2 で叩き起こす。stderr の文面がそのままモデルに渡る。

```json
"hooks": { "Stop": [ { "hooks": [ {
  "type": "command",
  "command": "~/Development/hitsudan/Tools/board-wake.sh",
  "asyncRewake": true,
  "timeout": 1830
} ] } ] }
```

- 未回収の依頼（`~/.hitsudan/requests/<key>.json`）が無ければ、即 exit 0 で何もしない。
- キーの求め方は MCP サーバと同じ。
    - フック側で同じ値が手に入る保証は無い。
    - そのため、セッション ID（環境変数と stdin）とパスのハッシュ（解決後・解決前）を候補にし、
      実際に依頼ファイルがあるものを使う。
- 待ち役はセッションごとに 1 つだけなので、停止のたびに監視プロセスが増えることはない。
    - ロックは `requests/<key>.lock/` ディレクトリで、中に pid と期限を置く。
    - 今の待ち役の期限では依頼の掲示期限まで足りないときは、新しいフックが引き継ぐ。
      旧い待ち役は自分で降りる。
    - 起こす権利は `mkdir` で1つだけ取るので、引き継ぎの瞬間にも二重には起こさない。
- `wait_for_board` で同期的に待っている間は起こさない。
    - その返信は `wait_for_board` 自身が受け取るため。
- 依頼の掲示期限を過ぎたら自分で終わる。

これで `request_board` → 別作業 → ユーザーが書いて送信 → **セッションが自動で起きて
`collect_board`** という、イベント駆動の往復が成立する。

### MCP の sampling は使えない

Claude Code 2.1.260 のクライアントに `sampling/createMessage` は実装されていない。
申告 capabilities に無いだけでなく、実際に投げると `-32601 Method not found` が返る
（`Tools/samplingprobe.swift` で再現できる）。あるのは `roots` と `elicitation` だけ。
CLI にも実行中セッションへの注入口は無い。

MCP クライアントの申告内容は `~/.hitsudan/mcp-client.json` に毎回記録しているので、
将来 `sampling` が生えたらそこで気づける。

`wait_for_board` はクライアント側のツールタイムアウトで落ちないよう、既定 55 秒で
**エラーではなく**「まだ」を返す。依頼文はその後も約 60 秒ボードに残るので、
そのまま呼び直せば待ち続けられる（同じセッションの呼び直しではボードを前面に出し直さない）。

### 依頼は一度に1つ、返信は宛先ごと

- ボードに出せる依頼は一度に1つ。
    - 別のセッションが依頼すると「表示中です」のエラーが返る。黙って置き換えない。
- 返信はセッションごとのキーで分けて保存する。
    - キーは `CLAUDE_CODE_SESSION_ID`、無ければプロジェクトの絶対パス（シンボリックリンク解決後）のハッシュ。
    - 他のセッションの返信を受け取ることはない。
- 返信は回収されるまで残る。
    - `read_board` を先に呼んでも消えない。
- 依頼の掲示期限は最長 1800 秒（Stop フックが見張れる長さに合わせてある）。
    - 期限切れやアプリの再起動で依頼が消えたら、`collect_board` が「出し直して」と返す。
- タブレットが繋がっていないときはボードを前面に出さず、「依頼は登録済み」と返す。
    - 繋がった時点で表示される。

### 上書きは必ずユーザーが決める

`show_on_board` と `clear_board` は**即座に反映しない**。送られた内容はボードに
**半透明のプレビュー**として乗り、`適用` / `破棄` の大きなボタン（ペンで押せる大きさ）が出る。
ユーザーが押すまで確定しない。セッション側には `pending: true` が返る。

未回答の提案に新しい提案が来たら、前の提案は「取り下げ」として記録し、待っている側にもそう返す。
ページをめくっても、提案のプレビューと依頼文は消えない（ページではなくボードに属するため）。
適用した提案の一行（`notice`）は、適用後は残さない。

### アプリと MCP の橋渡し

ソケットではなくファイルベース。どちらが再起動しても壊れない。

```
~/.hitsudan/inbox/<id>.json        セッションからの命令
~/.hitsudan/outbox/<id>.json       アプリの返答
~/.hitsudan/replies/<key>.png|json 「送る」で書かれるセッション宛ての返信（回収で消える）
~/.hitsudan/proposals/<id>.json    提案の結果（適用 / 破棄 / 取り下げ）
~/.hitsudan/requests/<key>.json    未回収の依頼の記録（Stop フックが見る）
~/.hitsudan/board.png              最後に公開したシート（read_board・クリップボード用）
~/.hitsudan/board.json             { seq, savedAt, note }
~/.hitsudan/state.json             接続とキャンバスの状態
```

- 書き込みはすべて一時ファイルに書いてから rename する。
    - 書きかけを相手が読むことはない。
- アプリは inbox を kqueue（`DispatchSource`）で監視する。
    - 取りこぼし対策の確認は 5 秒ごとだけで、何も起きていない間はほぼ起床しない。
- MCP サーバも、返答や返信をディレクトリ監視で待つ。
    - 取りこぼし対策の確認は 3 秒ごと。
- 起動時に inbox と outbox を掃除し、取りに来られなかった返答は時間で掃除する。
    - 前回の残骸が新しい命令に見えることはない。
- `seq` は起動時に `board.json`・`state.json`・返信ファイルの最大値から復元する。
    - どれかが壊れていても 0 に戻らない。
- MCP サーバは stdin を読むスレッドとツールを実行するスレッドを分けている。
    - 待っている最中でも `notifications/cancelled` と `ping` に応じる。
    - キャンセルされた `wait_for_board` は依頼を取り下げる。

## 動いている Claude セッションへ流す（MCP が使えない場合）

CLI には外部からセッションへ注入する口がない。

- 「送る」（⌘Return）は、返信と同時にボードを画像としてクリップボードにも置く。
    - Claude Code の入力欄で ⌘V すれば貼れる。
    - テキストを同時に載せるとターミナルがそちらを優先するので、画像だけを載せている。
    - ただし「送る」は依頼を出しているセッションがあるときしか押せない。
- MCP サーバは**セッション開始時に接続される**ので、登録前から動いているセッションには
  ツールが出てこない。
    - その場合は ⌘S で PNG に書き出して渡す。

## HUION Kamvas 13 Gen3 プロトコル（実測）

USB `VID 0x256C / PID 0x2008`, Product `Huion Tablet_GS1333`。HID インターフェースは3面。

| # | UsagePage/Usage | 用途 |
|---|---|---|
| 0 | `0x01`/`0x0E` | ダイヤル系（report `0x11`） |
| 1 | `0x0D`/`0x02` | 標準デジタイザ（report `0x0A`）＋ express key の keyboard report `0x03` |
| 2 | `0xFF00`/`0x01` | ベンダー面（input `0x08`, feature `0x16`） |

タブレットは2つのモードを持ち、本アプリは両方を解釈する。

### ベンダーモード — report `0x08`, 14バイト
HUION ドライバが起動時に切り替えるモード。

```
[0]  0x08
[1]  bit0 ペン先 / bit1 ボタン1 / bit2 ボタン2 / bit3 ボタン3 / bit7 近接
     0x00 = 圏外, 0x80 = ホバー, 0x81 = 接地
[2:4]  X    u16 LE   0..58760
[4:6]  Y    u16 LE   0..33040
[6:8]  筆圧 u16 LE   0..16383
[8:10] 未使用（常に 0x0000）
[10]   X傾き  int8   ±60
[11]   Y傾き  int8   ±60
[12]   ツール種別（ペン = 0x03）
[13]   未使用
```

X 0..58760 / Y 0..33040 は実測。有効エリア 293.76 × 165.24 mm に対し **5080 LPI**（200 units/mm）で計算が合う。
筆圧 16384 段階は公称値と一致。`0x82` / `0x84` / `0x88` は筆圧ゼロのまま出るので、接地ではなくボタン3系統。

byte[1] のビット 4〜6 が立っているレポート（`0xE0` 本体キー / `0xF0` タッチストリップ /
`0xF1` ダイヤル。Linux の hid-uclogic による）はペンのサンプルとして読まずに捨てる。
ペンの状態値はビット 0〜3 と 7 しか使わないので衝突しない。この3値は実機で未計測。

### 標準デジタイザモード — report `0x0A`, 10バイト
ベンダードライバがない状態での既定モード。HID Report Descriptor から読める。

```
[0]  0x0A
[1]  bit0 ペン先 / bit1 サイドボタン / bit2 消しゴム / bit3 反転 / bit6 近接
     実測値は 0xC0 = ホバー, 0xC1 = 接地（bit7 は Descriptor 上パディングだが常に立つ）
[2:4]  X    u16 LE   0..32767
[4:6]  Y    u16 LE   0..32767
[6:8]  筆圧 u16 LE   0..16383
[8]    X傾き int8
[9]    Y傾き int8
```

**これが重要な結論**: 標準モードでも筆圧 16384 段階と傾きが出る（実測で 1781→16330 まで確認）。
つまりベンダードライバを外しても、筆圧・傾きは失われない。

ただし失われるものが2つある。

1. **NSEvent の筆圧** — ベンダードライバは筆圧付きの tablet イベントを合成していた。
   外すと `event.pressure` が 0 で来るので、NSEvent 頼みの実装は線が消える。
   本アプリは生 HID を読むのでこれに依存しないが、HID が受け取れないときの
   フォールバックでは「筆圧情報なし」とみなして一定幅で描く。
2. **筆圧カーブ** — 生センサ値は軽いタッチ側が極端に非線形。ドライバが当てていた
   カーブは `CanvasView.pressureCurve`（ガンマ）として自前で持つ。既定 0.65。

### 入力監視の許可と署名

アドホック署名だとビルドのたびに cdhash が変わり、TCC の許可が毎回無効になる
（`IOHIDCheckAccess` が「拒否」になり、許可ダイアログも出なくなる）。
そこで**安定した自己署名鍵**で署名している。

```
designated => identifier "local.hitsudan.board" and certificate leaf = H"6a2771bc…"
```

要件に cdhash が入らないので、再ビルドしても許可が生き続ける。

鍵は login キーチェーンの `Hitsudan Local Signing`。控えは `~/.hitsudan/signing/`。

**署名鍵の再作成**（キーチェーンから消えた場合）:

```sh
cd ~/.hitsudan/signing
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -config cert.cnf -keyout key.pem -out cert.pem
openssl pkcs12 -export -out id.p12 -inkey key.pem -in cert.pem -passout pass:hitsudan \
  -name "Hitsudan Local Signing" -certpbe PBE-SHA1-3DES -keypbe PBE-SHA1-3DES -macalg sha1
security import id.p12 -k ~/Library/Keychains/login.keychain-db -P hitsudan -A
```

macOS の `security import` は OpenSSL 3 の既定の PKCS#12 を読めないので、
`-certpbe/-keypbe/-macalg` の指定は必須。証明書を作り直すと要件が変わるので、
入力監視の許可は取り直しになる。

**許可が「拒否」で固まったら**: 一度拒否になると `IOHIDRequestAccess` はダイアログを出さない。
システム設定 → プライバシーとセキュリティ → 入力監視 から `筆談ボード` の項目を
**「−」で削除**してからアプリを再起動する。

### 状態の確認先

アプリは2秒ごとに `~/.hitsudan/hid-status.log` に自分の状態を書く。

```
入力監視 許可 / open 成功  デバイス=検出  最終サンプル=0.1秒前  モード=HID digitizer 0x0A
割当=Kamvas 13  画面=Kamvas 13|…
```

排他確保・マウス制限・アクセシビリティの状態も同じログに出る。
設定ウィンドウの「ペンの生データ」にも同じ内容が出る。

## ペンの割り当て先ディスプレイ

ベンダードライバが無いと、macOS は汎用デジタイザを**カーソルがいるディスプレイ**に
割り当てる。マウスを別の画面に動かすとペンの反映先も動いてしまう。

対策として、生 HID の絶対座標を指定ディスプレイに自前でマッピングしている。
設定ウィンドウの「ペンの割当先」で選ぶ:

- **自動** — 名前に kamvas / huion / gs1333 を含むディスプレイを探して使う
- **各ディスプレイ名** — 手動指定

選択は表示位置ではなくディスプレイの UUID で `UserDefaults` に覚える（`penDisplay`）。
ディスプレイを抜き差ししても別の画面にずれない。選んだディスプレイが抜けている間は
「（未接続）」付きで選択を残す。以前の「カーソル追従」の保存値は自動に読み替える。

割当先が見つからないときだけ、排他確保とマウス制限を外して macOS に任せる
（このときだけ OS のカーソルがペンに追従する）。一瞬消えただけで開き直しを
繰り返さないよう、外すまで 1.5〜3.5 秒待つ。

ペンで描いている間はマウスからの描画を無視する（二重ストロークを防ぐため）。
生 HID が 2.5 秒途切れたら自動でマウスに戻すので、描けなくなることはない。

デジタイザの原点は上辺基準。`CGDisplayBounds` も左上原点・y下向きなので、変換は不要。

## Kamvas をボード専用にする

macOS から Kamvas をディスプレイとして消すと、ボード自体も描けなくなる。
そこで「画面としては残すが、ペンはボードにだけ効き、マウスは入れない」形で専用にしている。

**デバイスの排他確保** — タブレットが読めて割当先ディスプレイがある間は常に、
`IOHIDManagerOpen` に `kIOHIDOptionsTypeSeizeDevice` を渡して開く。
root は不要で、入力監視の許可だけで通る。これをしないと macOS 自身が同じレポートから
システムのカーソルを動かしてしまう。

- 排他確保に失敗したら、排他なしで読み続ける。
    - このときは「macOS がペンでカーソルを動かします」と状態に出し、マウス制限も外す。
    - 制限を残すと、ペンが動かすカーソル自身を弾いてしまうため。
- 失敗後は、タブレットを挿し直すか割当先を選び直すまで再試行しない。
    - 再試行のたびにデバイスを開き直し、描いている線が切れるため。
- 開けなかったことの通知は、次のランループの番に遅らせる。
    - 同期で呼ぶと処理が入れ子になり、状態が壊れるため。

**ペンはシステムのカーソルを動かさない** — 描画は生 HID からキャンバスへ直接入れる。
紙の外（パネルのボタン、ページ送り、適用 / 破棄、設定シート、確認ダイアログ）を押したときは、
ペン先の真下にある自分のウィンドウへ、マウスの押下・ドラッグ・離しの合成イベントを
`NSApp.postEvent` で送る。他アプリのウィンドウには何も送らない。

- 押下に対応する離しは必ず送る。
    - 送る場面は、ペンが離れたとき、HID が途切れたとき、ディスプレイが消えたとき、抜いたとき、終了時。
- ボードが隠れているとき、シートやモーダルが前にあるとき、ペン先が自分のウィンドウに無いときは描かない。

**マウス制限** — `MouseBarrier` がマウス移動とドラッグのイベントタップ（アクティブ）を
専用スレッドで動かす。移動先が Kamvas に入ったら、来た側のディスプレイの端へ座標を押し戻し、
`CGWarpMouseCursorPosition` でカーソルも戻す。

- タップの時点でカーソルはもう動いているので、座標の書き換えだけでは止まらない。だからワープも要る。
- ワープ直後に `CGAssociateMouseAndMouseCursorPosition(1)` を呼ぶ。
    - ワープ後に約 0.25 秒マウスが止まるのを避けるため。SDL・Wine と同じ方法。
    - この環境で効くかは実機で未確認。壁に押し当て続けて引っかかるなら、ここを疑う。
- 1回の移動で Kamvas を飛び越えた場合も、入ったものとして押し戻す。
    - Kamvas が2枚の画面に挟まれる配置では、マウスは反対側の画面へ行けない。
    - Kamvas はディスプレイ配置の端に置くこと。
- メインスレッドが詰まってもシステム全体のマウスが引っかからないよう、タップは専用スレッドで回す。
- システムがタップを止めたら（タイムアウト・セキュア入力）すぐ再開する。
- タブレットの USB を抜いても、Kamvas のディスプレイが残っていれば制限は続ける。
- アクティブなイベントタップにはアクセシビリティの許可が要る。
    - 未許可なら起動ごとに1回だけダイアログを出し、状態行とメニューバーに表示する。
- 次の場合は制限をかけず、理由を状態に出す。
    - Kamvas がミラーリング中
    - 他にディスプレイが無い
    - Kamvas がメインディスプレイで、かつ「ディスプレイごとに個別の操作スペース」がオフ

マウスが入れないので、他アプリのウィンドウを Kamvas へドラッグして持ち込むこともできない
（端まではドラッグできるので、一部がはみ出すことはある）。

設定は、マウスの届く別のディスプレイにウィンドウとして開く（他にディスプレイが無いときだけ、
ボード上のシートで開く）。ポップアップのメニューは独自の追跡ループで動き、ペンの合成クリックが
届く保証が無いので、Kamvas 上で開くと閉じられなくなるおそれがあるため。

**express key** — 「そのまま通す」に割り当てたキーは、排他確保中だけ自前で再送する
（排他していないときは OS がそのまま届けるので、再送すると二重になる）。
再送したキーには、排他の状態に関係なく keyUp を必ず1回送る。切断時は押下中のキーを離す。

**ランループのモード** — HID デバイスは `commonModes` にスケジュールすること。
`defaultMode` だと、AppKit がボタン押下やメニュー表示でイベント追跡ループに入っている間だけ
ペンのレポートが止まり、離しても `mouseUp` が生成されない。

サイドボタンや express key の右クリック・中クリックの割り当ては、排他確保中はボード上の
ペン位置に送る（ペンが圏外なら何もしない）。

## CI

`.github/workflows/build.yml`。`main` への push、`v*` タグ、プルリクエスト、
手動実行（workflow_dispatch）で動く。

- 図形認識の判定テスト（`Tools/run-tests.sh`）
- ユニバーサルビルド
- 成果物の検証 — arm64/x86_64 の両方が入っているか、`minos` が 13.0 で
  Info.plist の申告と一致するか（実体が 26.0 なのに plist が 13.0 と嘘を
  ついていたことがある。スライスごとに剥がして確かめる）、アイコンの有無、
  署名の検証
- MCP サーバに実際に JSON-RPC を流して 7 ツールを申告するか確認
- `Hitsudan.app.zip` をアーティファクトに

**`v*` のタグを打つと**、署名 → 公証 → Release への添付まで自動で走る。

- 権限
    - ワークフローの既定は `contents: read`。
    - Release を作るのは、`contents: write` を持つ別ジョブ `release`（タグのときだけ、`build` の後）。
    - checkout は `persist-credentials: false`。
- 署名と公証の両方が揃わないタグは**プレリリース**として公開する。
    - `/releases/latest` はプレリリースを返さないので、自動更新が拒否する zip を勧めることはない。
    - 同じタグを再実行したとき、latest が一瞬でも拒否される zip を指さない順序で更新する。

```sh
git tag v1.0.0 && git push origin v1.0.0
```

### 署名と公証に必要な Secrets

`MACOS_SIGN_IDENTITY` が未設定なら CI は通る（アドホック署名にフォールバックし、
Release にもその旨が書かれ、プレリリースになる）。設定すると Developer ID 署名と公証が有効になる。

**指定した識別名がキーチェーンで見つからない場合、`build.sh` はアドホックに
落ちずにその場で失敗する。** 黙って落ちると、署名済みのつもりのものが配られて
しまうため。CI 側でも、`MACOS_SIGN_IDENTITY` を指定したときは実際に
`Developer ID Application` で署名され、ハードンドランタイムが付いているかを
確かめている（`codesign --verify` はアドホック署名でも通ってしまうので、
それだけでは足りない）。

Release ノートは成果物に聞いて書き分ける。署名の有無は `codesign`、公証の有無は
`stapler validate` で判定するので、「署名だけして公証していない」状態
（`APPLE_API_KEY_ID` などが未設定のままタグを打った場合）もそのまま書かれる。

| Secret | 中身 |
|---|---|
| `MACOS_SIGN_IDENTITY` | `Developer ID Application: 名前 (TEAMID)` — `security find-identity -v -p codesigning` に出る文字列そのまま |
| `MACOS_CERTIFICATE_P12` | Developer ID Application 証明書と秘密鍵を書き出した `.p12` を base64 にしたもの |
| `MACOS_CERTIFICATE_PASSWORD` | その `.p12` のパスワード |
| `APPLE_API_KEY_ID` | App Store Connect API キーの Key ID |
| `APPLE_API_ISSUER_ID` | 同じく Issuer ID |
| `APPLE_API_KEY_P8` | `AuthKey_XXXXXXXX.p8` を base64 にしたもの |

準備手順:

```sh
# 1. Xcode か developer.apple.com で「Developer ID Application」証明書を作る
#    （Apple Development ではなく Developer ID。配布用はこちら）

# 2. キーチェーンアクセスで証明書と秘密鍵を選び、.p12 に書き出す
base64 -i DeveloperID.p12 | pbcopy      # → MACOS_CERTIFICATE_P12

# 3. 識別名を確認する
security find-identity -v -p codesigning  # → MACOS_SIGN_IDENTITY

# 4. App Store Connect → ユーザーとアクセス → 統合 → App Store Connect API で
#    「Developer」ロールのキーを作り、.p8 をダウンロード
base64 -i AuthKey_XXXXXXXX.p8 | pbcopy   # → APPLE_API_KEY_P8

# 5. gh で登録
gh secret set MACOS_SIGN_IDENTITY
gh secret set MACOS_CERTIFICATE_P12
gh secret set MACOS_CERTIFICATE_PASSWORD
gh secret set APPLE_API_KEY_ID
gh secret set APPLE_API_ISSUER_ID
gh secret set APPLE_API_KEY_P8
```

公証には**ハードンドランタイム**とタイムスタンプが要るので、`HITSUDAN_SIGN_IDENTITY`
が指定されているときだけ `codesign` に `--options runtime --timestamp` を付ける。
ローカルの自己署名ビルドには付けない。

なお HID の読み取り（IOHIDManager）、イベントタップ、イベント生成はハードンドランタイムでも
entitlement を必要としない。必要なのは TCC の許可（入力監視・アクセシビリティ）だけ。
アクセシビリティはマウス制限のイベントタップにも使う。

**Developer ID で署名すると、いま与えてある入力監視とアクセシビリティの許可は
一度取り直しになる**（署名要件が変わるため）。ただしそれ以降は自己署名鍵より確実に
安定する。

## 自動更新

メニューバー → **アップデートを確認…**。GitHub Releases の `latest` を見て、
タグが Info.plist の `CFBundleShortVersionString` より新しければ差し替える。
起動時に勝手に通信することはない（確認は手動のときだけ）。

バージョンはタグから焼き込まれる。CI はタグビルドで `HITSUDAN_VERSION` を渡し、
一致しているかを検証ステップで確かめる。手元ビルドは直近のタグ、タグが無ければ
`0.0.0` になる。

### 前提：リポジトリか Release が公開されていること

**いまこのリポジトリは非公開なので、自動更新は動かない。** 匿名の API アクセスは
404 になる（403 ではない）。トークンをアプリに焼き込むわけにはいかないので、
使うにはリポジトリを公開するしかない。公開するまでは、確認しても
「リリースが見つかりません」と出る。公開していても、プレリリースしか無いうちは同じ表示になる。

### 差し替える前に何を確かめているか

落としたものをそのまま起動すると、配布経路を乗っ取られた時点で任意コード実行に
なる。`Sources/Updater.swift` は差し替え前に次を確かめ、1つでも欠けたら中止する。

| 確認 | コマンド | 何を防ぐか |
|---|---|---|
| 署名が壊れていない | `codesign --verify --deep --strict` | 転送中の破損・改竄 |
| 公証されている | `spctl --assess --type execute` | 署名だけ付け替えた別物 |
| Team ID が自分と同じ | `codesign -dvv` の `TeamIdentifier` | 他人の正規に公証されたアプリへの差し替え |
| 同じ開発者・同じアプリ | `codesign --verify -R='anchor apple generic and <Developer ID の OID> and certificate leaf[subject.OU] = "<TeamID>" and identifier "<識別子>"'` | Gatekeeper を切った Mac での素通り、表示文字列の比較の弱さ |
| `.app` が実体のディレクトリ | `resourceValues` の `isSymbolicLink` / `isDirectory` | zip 直下のシンボリックリンクで検証だけ正規版に向けること |

`codesign --verify` はアドホック署名でも通るので、それだけでは足りない。公証と
コード要件の確認が実質的な関門になる。Team ID と識別子は実行中のアプリ自身の署名から読む。

アドホック署名の手元ビルドは、`TeamIdentifier` が `not set` なので自動更新の
対象外（更新しようとすると中止して理由を出す）。配布物を受け取る側も、
Developer ID 署名されたものだけが更新される。

差し替えは `replaceItemAt` で行い、`/Applications` に書き込めない場合はその旨を
出して何もしない。更新後は同じ署名なので、入力監視とアクセシビリティの許可は
通常そのまま引き継がれる。

再起動は、旧プロセスの終了を待ってから新しい方を開く（切り離した小さなシェルが
旧プロセスの pid を見張り、終わったら `open` する。パスは引数で渡す）。
新旧が重なると、新しい方がタブレットの排他を取れないため。
終了時には保存待ちのページを書き出す。

## 図形補正

描いたあとペンを離さずに 0.55 秒静止すると、直線・円・四角・三角に整形される。
整形後もペンを離すまで伸縮できる（三角は角の取り方が一意でないので固定）。

「静止」は、最後に動きを記録した位置から 4 紙面単位（約 0.7mm）以内に留まること。
直前のサンプルとの差で測ると、ゆっくり描いているだけで静止とみなされてしまうため。
整形した瞬間のペン位置と、動かす角とのずれを覚えておき、以後の伸縮はそのずれを
保ったまま行う（円や四角は書き始めの点が輪郭上にあり、角には無いため）。

判定は $1 Unistroke Recognizer（Wobbrock, Wilson & Li, UIST 2007 / New BSD）の移植。
`Sources/DollarRecognizer.swift`。**何を描いたか**は認識器が決め、**どこにどの大きさで**
置くかは `CanvasView` 側が実際の点に当てて決める。

移植にあたっての変更点:

- 閉じた図形は開始位置に敏感なので、4つの開始点 × 2方向でテンプレートを登録している
- 外接矩形を正方形に引き伸ばす正規化は、高さがほぼゼロの直線でノイズを縦に極端に
  増幅する。縦横比が 0.3 未満のストロークは等方スケールにした（論文が1次元ジェスチャに
  ついて述べている注意点）。これでスコアが 0.77 → 0.99 になった

しきい値 0.88 は実測で決めた。`Tools/rectest.swift` が合成ストロークで検証する:

```
直線     → line       0.99
円       → circle     0.96–0.98
四角     → rectangle  0.94–0.97
三角     → triangle   0.93–0.97
不定形   → (誤判定)    0.81–0.84
なぐり書き → (誤判定)    0.43–0.79
波線     → (誤判定)    0.62–0.65
```
